### 第 4 页：转换核心服务于两个客户端（约 75 秒）

### 第 5 页：当前阻塞：转换进程缺少诊断（约 80 秒）

第一部分最后聚焦当前最具体的故障。截图里有两条信息，一条是 CONVERTER_FAILED，另一条是编号清理风险警告。它们不能被直接连接成因果关系。runner 在无法把标准输出解析成 JSON 时返回通用失败，这意味着转换进程可能没有正常启动，也可能在输出结果前异常退出。与此同时，编号警告来自配置，在任务开始前就可能生成，它只说明标题数字存在被删除的风险。正确定位顺序是先用最小 Markdown 对照，再检查 doctor、基础沙箱探测和带 limit_exec 的真实转换。诊断记录应限字节、限时，并只对管理员开放，不能把原文、主机路径或凭证直接返回给网页。这个问题也说明，增加界面之后必须补齐运行诊断。接下来第二位同学会从模块和 C4 层次解释，这些诊断分别属于哪一层。

## 第 3 位：数据流与故障影响（第 11–15 页，计划 6 分 25 秒）


### 第 11 页：一次转换的完整流程（约 75 秒）

第三部分用一份文档说明完整流程。浏览器先读取文件，必要时创建临时会话，然后带幂等键提交任务。服务端检查清单、配置、字节预算和图片，再写入工作区与 SQLite。此时返回二零二，含义只是任务已经受理。内部执行循环取到 queued 任务后才开始运行 CLI，阶段变化持续保存，浏览器定时查询。转换结束后，服务会检查结果是不是符合约束的 DOCX，计算大小和摘要，再保存终态并清理输入。用户最后通过归属校验下载，浏览器还检查下载字节数，在支持的安全上下文中校验 SHA-256。流程里每个成功的含义都不同：上传成功、查询成功、转换成功和本地保存成功不能混为一谈。如果批量任务中有部分成功，失败不会抹掉此前的有效产物。后面的状态与清理规则必须围绕这些区分设计。

### 第 12 页：从入口到落库的写入顺序（约 80 秒）

这一页专门解释落库，因为文件与数据库的顺序影响恢复。Guard 先在内存里收集有界请求体，路由解析后在 staging 写 Markdown、图片和配置。图片验证通过之后会再次检查幂等，因为异步等待期间可能有相同请求进入。接下来把目录 rename 到正式 jobs 路径，再通过 Store.insert 的事务保存任务和会话续期。目录 rename 在同一文件系统内具有原子性，但它与 SQLite 提交不是同一事务。如果进程在两者之间崩溃，可能留下没有数据库引用的目录。启动逻辑会扫描并清理无主目录，也会把上次 running 或 cancelling 的任务标成重启失败。这里不能宣称实现了任意崩溃点无损续跑。后续拆 Worker 时，需要把领取、文件可见性和恢复协议设计清楚，而不仅仅换一个数据库。

### 第 13 页：数据生命周期与访问边界（约 75 秒）

文档的数据有不同生命周期。会话 token 在客户端，服务只保存哈希，默认有效期四十八小时，提交任务会延长服务端访问期。Markdown、图片和有效配置在任务私有目录里，进入终态后执行清理。DOCX 默认保留二十四小时，用户也能主动删除。SQLite 保存状态、原始文件名等必要元数据以及摘要，不保存正文和 token 明文。删除或过期时会把任务改成小型墓碑，之后按清理规则再保留约二十四小时，用于拒绝旧幂等请求重放。浏览器只记配置和最近任务 ID，不持久保存未上传文本。这里还有一个必须诚实说明的限制：部分文件清理调用忽略错误，不能仅凭逻辑终态保证所有字节已经物理删除，备份也可能延长实际保留。因此需要清理滞后指标和失败告警，并为备份单独制定期限。

### 第 14 页：外部依赖按阶段区分（约 75 秒）

外部依赖应按阶段分析。GitHub 和各类软件源是在构建部署时使用，前面虚拟机拉取源码遇到连接重置，影响的是更新，不会自动让已部署的版本停止转换。DNS、TLS 和可选反向代理属于用户访问入口，如果它们故障，用户可能无法连接，但后端进程本身仍可能正常。Pandoc、python-docx 和 lxml 是本机运行依赖，不是外部 SaaS。Bubblewrap 则依赖 Linux 的内核与安全策略，如果不可用，服务应拒绝任务，不能为了看起来成功而关闭隔离。SQLite 和磁盘是单机故障点，容量不足和写入异常会影响受理或查询。还有一个有意的取舍：系统不会联网下载 Markdown 中的远程图片，这减少了网络不稳定与 SSRF 攻击面，但用户需要把本地图片随文档上传。依赖分析必须同时讲可用性和功能代价。

### 第 17 页：Workers 的边界是运行模型（约 80 秒）

官方文档说明，Python Workers 使用 Pyodide，也就是把 CPython 编译为 WebAssembly，再在 V8 isolate 内执行。这与我们当前依赖 Linux namespace、文件系统和 Pandoc 子进程的执行模型不同。免费 Workers 每天十万次请求，单次 CPU 时间十毫秒，内存是一百二十八 MB 每个 isolate，不是每个请求独享的预算。付费可以提高 CPU 时间上限，但仍然不会因此变成原来的 Linux 子进程环境。Pages Functions 也采用 Workers 的计费与运行约束，并不是另一种可以绕过问题的免费主机。对本项目而言，Workers 很适合返回静态网页或处理轻量入口，但若要完成原生转换，就需要把工作交给服务器或 Containers。理论上重新实现成纯 WASM 转换链是一条研究路线，但它需要重新验证依赖、排版一致性和性能，不能叫作本次小迁移。

一个可回退的发布流程从准备开始。我们应该使用独立版本目录，记录 commit、配置和依赖，先在隔离的数据目录做冒烟。现阶段发布需要暂停新提交并排空任务，然后切换代码与配置，启动唯一实例，验证健康、真实转换和下载。如果验证失败，回到保留的旧代码和旧运行环境。这里最危险的误区，是把回退理解成随手 git reset 或恢复一个旧数据库备份。代码可能已经依赖新字段，旧备份还可能抹掉发布后用户刚提交的任务。所以数据库变更应遵循先扩展、保持兼容、再切换、最后收缩的顺序，有破坏性变更时应单独制定数据恢复方案。回退演练还要检查运行进程和产物，不能只看网页恢复。当前脚本主要负责安装、构建和启动，这张图是待实现和演练的发布流程，不宣称已经具有一键回退能力。

### 第 30 页：验收门槛与团队校核（约 80 秒）

最后用验收门槛结束汇报。第一和第二位讲者核对产品边界、模块节点以及代码调用，确认图没有把未来目标画成现状。第三位负责真实转换、任务归属、清理与故障诊断，当前虚拟机错误仍是阻塞。第四位确认平台单价、演算假设和性能测试范围，避免把小样本或费用小计当成服务承诺。第五位维护 ADR，明确每个决定的状态、代价和重新讨论条件。第六位验证排空、版本记录与回退，不仅恢复网页，也要核对任务和数据。基于目前证据，我们建议先让自有服务器方案达到受控上线标准，再根据容量指标决定是否拆 Worker 或迁移 Containers。Cloudflare Workers 可以承担静态或入口角色，原生转换链不做无依据的直接搬迁。六个人完成事实校核后，再共同确认下一批的目标与责任人。
